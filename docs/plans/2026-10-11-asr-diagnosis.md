# 语音转文字不准：只读诊断 + 离线对比（第一阶段）

日期：2026-10-11　范围：只读，没动 `src/`、配置、守护进程；没录音没播放。
结论先行：**主病因在"段末二次识别"这一环，不在麦克风/噪声门**。三件事叠加：①二次识别用的 SenseVoice **2025-09-09 新版在这个场景比 2024-07-17 旧版差很多**；②二次识别吃的音频**头尾零缓冲**（流式有 0.5s 预滚 + 段后尾巴，二次识别没有），新版模型会丢首字/尾字；③唤醒词只看二次识别的结果，首字「管」一丢就叫不醒。

## 1. 无标答统计（mic 共 135 条；只有 46 条带 `stream_text`，更早的记录没有这个字段）

### ① 流式 vs 最终不一致（46 条里 32 条不同，占 70%）
| 类型 | 条数 | 样例（最终 ‖ 流式） |
|---|---|---|
| 完全一致 | 14 | 多是「管家」「唉」之类短句 |
| **最终丢了开头字** | ≥10 | 「天早上七点半叫我起床」‖「明天早上…」；「我老婆发微信…」‖「给我老婆…」；「在是几点了」‖「现在是几点了」；「家」‖「管家」（×2）；「我查一下…」‖「帮我查一下…」 |
| 最终丢了结尾字 | 2~3 | 「…驱动和我打」‖「…驱动给我打开」；「…给我安装完」‖「…安装完成」 |
| 同长度错字 | 12 | 「情天」‖「晴天」；「管他」‖「管家」 |
| 流式错、最终对 | 若干 | 「我的 H A L O 音响…」‖「我在摇音响…」；「你能不能听清我说的话」‖「…听听…」 |

**谁更可信？互有胜负，不能固定信任一边。** 用主人的 11 句（有标答）逐句比：流式赢 4 句（晴天/明天/带伞/给我老婆）、最终赢 3 句（HALO/现在几点了/帮我查…的国庆节放）、平 4 句；去掉主人说法与标答不一致的 3 句后，线上实录的 CER：最终 9.9%、流式 12.6%。**最终的系统性毛病是头尾丢字（有规律），流式的毛病是同音/中间错字（随机）**。

### ② 疑似截断（用 pool 的 raw/proc 看段头段尾，只统计 29 条有实质文字的段）
- 段尾**没有**在语音中间被切断：最后 100ms 能量占比 ≥0.3 的 **0/29**。
- 但 VAD 切得很紧：段头静音中位数 **40ms**、段尾静音中位数 **80ms**（p10 仅 60ms）；最后 200ms 里还有明显语音（≥0.5）的 4/29；头 100ms 已经是满音量（≥0.8）的 6/29 —— 起音贴着段边界。
- 噪声门归零不是主因：这 29 条里原始音频数字零占比 ≥30% 的只有 2 条（而且是英文 TTS 回灌那条和一条 8.7s 的杂音段）；主人那 11 句数字零占比 1%~7%，且没有一段在末尾 300ms 内出现 ≥10 个全零 10ms 帧（即 ≥100ms 的归零）。
- 补零实验直接证明"缺缓冲"（见 §4）：给二次识别前后各补 0.4s 零，丢首字的 3/3 句全部恢复（明天/给我老婆/帮我查一下），「管家帮我把…给我打开」「安装完成」这类尾字也有恢复。

### ③ 一句被拆成两段（相邻两段间隔 <1.5s）
- 候选 15 对（占相邻对 11%），例：「那个二三基本上不可」‖「因为他这不叫什么」(1.1s)；「一点多啦嗯」‖「管他」(0.9s，**唤醒词被单独切出去**)；「用用去点点关」‖「嗯」(0.8s)。
- 但 VAD 的 `min_silence=0.8s` 意味着任何 ≥0.8s 的停顿都会切开，这个口径判不出"同一句还是两句"：主人念的 11 句里相邻两句间隔也只有 0.9~2.6s（实际停顿比说好的 3s 短），每句都是单段、没有被拆。**目前没有证据说"拆段"是主因**，只是唤醒词和命令之间停顿 >0.8s 时会分成两段（靠免喊窗口兜）。
- 补充：若干 13~21s 的超长段是别人说话/电视声，识别全是乱字，和主人指令无关。

### ④ 专有名词/唤醒词
- **唤醒词「管家」（流式听见管家/官家的 10 次 + 1 次两边都错）**：最终正确 6/11；最终丢成「管他」「家」「家」「人家」的 4 次，流式都对。流式正确 10/11。
  - 「人家帮我把这个 H A L 的这个音响的驱动和我打」就是这个病：最终 `管→人`、`开` 丢尾；流式是「管家帮我把这个HAL的这个音响的驱动给我打开」。
  - wake 判定只用最终文本（`wake.py` 拼音容错能救「关家」，救不了「人家」「管他」「家」）。
- 漫步者 / 网易云 / 英雄联盟：流式与最终都对（2/2、2/2、2/2）。
- HALO：**最终输出被拆成「H A L O」带空格**（3/3 次）；流式输出「HALO」但有一次认成「我在摇音响」。字母带空格会让按词匹配的下游（关键词、热词）失效。
- TempoHub：主人那句还没被收到（见 §5）。
- 短碎音：25 条短/碎音里 15 条原始音频数字零 ≥30%——**「嗯」「我」「唉」「个」这类幻觉主要来自被音箱 DSP 噪声门掏空的静音段触发 VAD**（它们被碎音过滤丢掉了，不影响指令，但白耗一次识别 + 声纹）。池里 14 段「空」也是同一类（平均 48% 数字零）。

## 3. 离线对比脚本

`F:\coding\guanjia\scripts\asr_bench.py`（留在工作区，没有 git add）。子命令：

```
sync   # 补拷 segments 进 pool（去重）+ 合并 utterances
pool   # 生成无标答清单（pool 里全部段）
gold --start "2026-10-11 13:50:00" [--end ...]   # 标答集定位，生成 manifest_gold.jsonl
run --manifest <清单> --cands "sv_int8,sv_int8:raw,qwen3,sf_xingchen,..." [--exclude-idx 1,7,15] [--threads 3]
```

- 候选名：`sv_int8`（基准，与 `asr_final.py` 同配置）、`sv_int8_2024`、`sv_fp32`、`zip_stream`、`zip_stream_hot`、`para_int8`、`fire2`、`qwen3`、`qwen3_hot`、`sf_sensevoice`、`sf_telespeech`、`sf_xingchen`、`sf_xingchen_ultra`、`sf_qwen3`。
- 变体后缀：`:proc`（缺省）、`:raw`、`:raw_norm`、`:proc_pad`/`:proc_pad800`（前后补 0.4s/0.8s 零）、`:raw_pad`。
- 输出：`tmp\asr_eval\results\<名>.md/.json`（每段一行并排 + 汇总：CER、耗时、RTF）。CER 去标点空格、英文小写、阿拉伯数字与中文数词归一（「30」=「三十」，「30%」=「百分之三十」，「两」=「二」）。
- 云端 key 只在内存里读（环境变量 → `~/.claude/settings.json`（与 `front.py` 一致）→ openclaw.json），**不打印不落盘**；云端结果按"模型+音频哈希"缓存，不重复计费；掉线每分钟重试最多 5 次。
- 低优先级运行（Windows BELOW_NORMAL），默认 2~3 线程，没抢守护进程。
- 模型下载到 `F:\coding\guanjia\models\asr_eval\`（paraformer-zh-int8-2025-10-07、sense-voice 2025-09-09 fp32、sense-voice 2024-07-17 int8、fire-red-asr2 zh_en int8、qwen3-asr-0.6B int8），**没覆盖现有模型**。GitHub 在家里电脑只有 ~100KB/s，改走 hf-mirror（~8MB/s）。
- **局限（如实）**：
  1. sherpa-onnx 的 pip 版 onnxruntime 只有 CPU/Azure provider，**没用 GPU**（CPU 上这些模型都够快；如要 GPU 得另装 CUDA 版 sherpa 到独立 venv，目前没必要）。
  2. **Paraformer 在 sherpa-onnx 里不支持热词**（热词只给 transducer）；流式 zipformer 这个 2025-06-30 包是 BPE 建模、包里没有 `bpe.model`，热词文件编码失败，`zip_stream_hot` 实际等于无热词——我没有硬凑结果。热词只在 Qwen3-ASR 上有效（`qwen3_hot`，传 管家/漫步者/HALO/TempoHub/网易云/英雄联盟/周杰伦）。
  3. 流式 zipformer 离线只能喂 `seg.samples`，线上它还有 0.5s 预滚和 ~0.8s 真尾巴，所以脚本里给它补 1.0s 零近似；`zip_stream` 的数字**不代表线上流式**（线上实录流式见表首行）。
  4. 热词、FireRedASR 用的是 sherpa 支持的 **FireRedASR2 zh_en int8 AED（2026-02-26）**，没测旧版 large。

### 云端（硅基流动）
- 接口：`POST https://api.siliconflow.cn/v1/audio/transcriptions`，multipart：`file`、`model`；单文件 ≤1h/50MB。官方文档枚举只列 `FunAudioLLM/SenseVoiceSmall`、`TeleAI/TeleSpeechASR`；用主人的 key 查 `/v1/models?sub_type=speech-to-text` 实际可用：`FunAudioLLM/SenseVoiceSmall`、`XingChenAGI/XingChenASR-V3.2`、`XingChenAGI/XingChenASR-V3.2-Ultra`、`XingChenAGI/XingChenGSR-V1.0`、`XingChenAGI/XingChenASR-Diarize-V3.0`、`Qwen/Qwen3-ASR-1.7B`（`TeleSpeechASR` 也能调通）。

## 6. 推荐改法（按收益排序，均未执行）

1. **把二次识别模型换成 SenseVoice 2024-07-17 int8**（`asr_final.py` 里改 `MODEL_DIR`，API 不变，RTF 同级 ~0.04）。收益最大：CER 9.9%→3.6%，唤醒词首字不再丢，`HALO` 不带空格。注意输出会带标点/阿拉伯数字（「7点半」「30%」「2026年」），`wake.py`/`decide()` 和下游要能吃；上线前用更大的标答集再确认一次。
2. **给二次识别头尾补缓冲**：最小改法是前后各补 0.4s 零（`transcribe` 内部 `np.concatenate`）；更好的是在 `_frontend_step` 里给 16k 增益后的音频也维护一个环形缓冲（类似 `_raw_ring`），按 `seg.start−0.3s … 段尾+0.5s` 重新切一段喂二次识别，这样也不会是"假静音"。对新版模型必需，对旧版模型无害（偶有 ±1 字）。
3. **唤醒词判定做"双通道"**：`wake` 同时检查流式和最终文本，任一命中就当喊了（现在 4/11 的「管家」因最终丢首字被拒；改了 1、2 之后大多会自愈，但这是廉价保险）。
4. **一致性仲裁（可选）**：最终文本比流式短且流式包含最终的真子串时（丢头/丢尾特征），倾向流式，或把两者交给后面的 LLM 当"候选 A/B"；此项收益被 1、2 吃掉一大部分，先不做。
5. **挡掉被噪声门掏空的假触发段**：段内原始音频数字零 ≥30% 且段 RMS 90 分位 <0.02 时直接丢，不进 ASR/声纹（现在 15/25 条短碎音和 14 段「空」都是这类）。省算力、少「嗯/唉」。
6. **可选的第二档**：本地 Qwen3-ASR 0.6B int8（带热词，RTF 0.3）或云端 `XingChenASR-V3.2`（免费、1~1.6s、对静音最稳）只在"低置信度/含唤醒词争议"时才复核，不当主路径（延迟、网络、LLM 幻觉）。
7. **暂不建议**：流式 zipformer 热词（模型无 bpe.model，需重新导出）、Paraformer 热词（sherpa 不支持）、调 VAD 阈值（没有证据说主因在这）。

## 7. 代码质量与后续（供参考）

- `asr_final.transcribe` 的接口把"音频范围"完全交给调用方，是这次问题的根源；`_frontend_step` 同一份 `seg` 同时拿去给流式（带预滚）、二次识别（不带）、声纹（不带）、落盘，容易再出现"同一段三种口径"的问题。后续可以把"给识别的音频 = 段 + 前后缓冲"抽成一个小函数统一产出（我只给建议，没动）。
- `utterances` 只有一部分记录带 `stream_text`、没有记录"用的是哪个模型/是否补零/段起止时间"，建议后续把段起止（秒）和 ASR 模型名一并写进去，今天推间隔只能用 `t0 − 耗时` 近似。
- 离线脚本里用于对齐标答、CER 归一的函数是平台无关的纯逻辑，若以后要长期回归测试，可以再单独抽成 `eval` 小包；现在先留在 `scripts/`，不提交。
